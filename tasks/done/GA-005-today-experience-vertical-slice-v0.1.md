## Scope expansion (product-pass addendum, same task — no new GA task)

The original v0.1 acceptance below (a "Hoy" tab bolted onto the legacy nav)
was judged insufficient as a real product: it did not let the user
actually train, and the legacy UI remained the primary experience. This
task's scope was expanded, under the same GA-005 id, to deliver the full
gym-tomorrow journey — new primary nav (Hoy/Entrenar/Progreso/Perfil/Más,
Hoy as default), a redesigned Today/plan experience, and a new **active
workout execution flow** (start -> log sets -> advance -> finish ->
summary) — while keeping every prior acceptance criterion intact (real
3-engine pipeline, no duplicated domain logic, no inferred restrictions,
no Supabase/Edge Function/production change). See "Result (product-pass
addendum)" near the end of this file for what was actually built, and
`src/today-experience/README.md` for the full architecture. The task stays
in **REVIEW**, pending the user's own manual click-through, per the
instruction that accompanied this expansion.

## Objective

Expose the first visible GymApp 2.0 product surface: a "Hoy" screen inside
the existing app where a user provides today's training context and
receives a workout generated by the real Context Engine ->
Compatibility Engine -> Workout Planner pipeline.

## Context

`docs/REENGINEERING_DECISION_FRAME.md`'s target user journey calls for
"propose what to do today" to become visible product surface, not just a
domain module. GA-002/003/004 built the deterministic pipeline; this task
connects it to the existing GymApp UI as a real, working (if intentionally
minimal) vertical slice, per an incremental migration strategy that leaves
the legacy app fully intact.

## Scope

- A new integration layer (`src/today-experience/`): pure orchestration +
  view-model translation, plus one DOM-rendering file and one
  browser-entry bridge file.
- A demo/in-memory exercise catalog provider with a documented, explicit
  replacement seam for a future Gym-Exercise-Library-backed provider.
- Minimal `app.js` edits: one nav item, one `render()` branch, one small
  delegating function (`renderHoy`) — no domain logic added to `app.js`.
- One `index.html` edit: load the Today module as `<script type="module">`.
- Small additive CSS for the new screen's status banner/warning/caution
  styles.
- A browser-portability fix to `src/workout-planner/plan-id.mjs` (it used
  `node:crypto`, which does not resolve in a browser) plus a dedicated
  test for it.
- A zero-dependency local static file server (`tools/dev-server.mjs`) that
  serves `.mjs` with a correct JS MIME type, since the browser's native ES
  module loader requires it.
- Automated tests for the new pure orchestration/view-model logic.

## Out of scope

- Real Gym-Exercise-Library integration, the legacy 115-ID crosswalk,
  GA-001 HARD-001..005, any production Supabase/SQL change.
- Replacing the existing production workout generator.
- Deleting or disabling any existing screen/functionality.
- Reusing the real logged-in user's profile data for `trainingGoal`/
  restrictions (documented as deferred — see
  `src/today-experience/README.md`).
- A full visual redesign of GymApp.
- Persisting the generated plan (no Supabase write).

**Defect 1 — Fuerza/Abdomen generation failed on real medical/restriction
text.** Root cause (confirmed by code inspection, not guessed): in
`supabase/functions/generate-routine/index.ts`'s tool schema, `resumen`
(a free-text field the prompt demanded be clinically detailed) was
declared **before** `dias` (the actual routine). Claude emits structured
tool-call JSON in schema-declared field order, so a long, technical real
medical input — forcing a long, detailed `resumen` — could exhaust
`max_tokens: 4096` before `dias` was ever written, on both attempts
(same input, same prompt, no adaptation), for both Fuerza and Abdomen
(same shared, unconditional medical-reasoning prompt block). This is the
only code path that produces the exact observed text ("El modelo generó
una respuesta inválida dos veces seguidas").

Fix: reordered the schema (`dias` before `resumen`), capped `resumen` to
~3 sentences in the prompt, raised `max_tokens` to 8192, and replaced the
blind identical-retry with an adaptive one — attempt 2 now gets the
actual validation errors fed back via a proper `tool_result` conversation
turn, so it has a real reason to produce something different instead of
repeating the same mistake. The day-count check was relaxed from exact
match to a maximum (fewer days is an acceptable safety-driven adaptation;
more is not) — deterministic contraindication/catalog/equipment checks
are untouched and exactly as strict. Added bounded, non-PII diagnostic
logging (`stop_reason`, day count, a 300-char capped sample — never the
user's medical text or full model output). Error responses now carry a
machine-readable `codigo` (`RESPUESTA_TRUNCADA`/`VALIDACION_FALLIDA`);
`app.js`'s new `mensajeErrorGeneracionAmigable()` maps these to the
non-technical message the task specified, never showing raw
validation/model internals as the only explanation.

**Prompt reinforcement:** explicit line added stating this is NOT a
rehabilitation-protocol generator and the free text is not a diagnosis to
verify — its only job is adapting a normal strength/core routine around
excluded movement patterns. No new rehab capability was built or implied.

**Defect 2 — navigation lost in-progress generation.** Root cause:
`invocarGeneracionFuerza`/`generarRutinaAbdomenDesdeGenerador`/
`generarRutinaCardioDesdeGenerador` held loading/message state in local
DOM element references (`document.getElementById(...)`) captured at call
time. Navigating away calls `render()`, which replaces `app.innerHTML`,
destroying those nodes — the network request continued in the background,
but its result/error had nowhere left to render.

Fix: introduced `estado.generacion.{fuerza,abdomen,cardio}` (global state,
survives any screen change) and a persistent `#indicador-generacion`
container in `index.html`, deliberately **outside** `#app` so it's never
destroyed by a screen switch. All three generation functions unified into
one `invocarGeneracion(tipo, nombreFuncion, body)` that: guards against a
duplicate call while one is already active, updates `estado.generacion`
(never a captured DOM node), and always calls the lightweight
`actualizarIndicadorGeneracion()` regardless of current screen. A subtle
global banner ("Generando rutina de Fuerza…") now shows on every screen
while active. `renderGenerador()`'s buttons/messages now read from
`estado.generacion` on every render instead of being mutated directly.

**Files changed (this pass):** `app.js` (generation state + indicator +
unified `invocarGeneracion`), `index.html` (indicator container),
`styles.css` (banner styles), `supabase/functions/generate-routine/index.ts`
(schema reorder, prompt, adaptive retry, relaxed day-count check, `codigo`
fields, diagnostics).

**Validation performed:** the Edge Function has no existing Deno test
harness in this repo, and `app.js` has no existing DOM test harness either
(both pre-existing gaps, not introduced by this change) — introducing one
tonight for a two-defect fix was judged disproportionate scope, per "do
not spend time writing broad low-value tests." Validated instead via: a
full TypeScript type-check of the Edge Function (`tsc --noEmit`, 0 errors,
using a Deno/fetch/Response global shim since no Deno binary is available
in this environment), `node --check app.js` (clean), careful manual
tracing of both fixes against the exact reported reproduction, and the
full existing suite re-run unchanged:
```
69/69 passing (unchanged — neither fix touches src/*)
```
`git diff --check` clean.

**Still unverified: the actual Anthropic API call.** No Deno runtime,
Supabase project, or Anthropic credentials are available in this
environment, so the fix could not be exercised against the real model.
The schema-reorder/token/retry logic is verified correct by static
analysis and matches the code-level evidence exactly, but real-browser
